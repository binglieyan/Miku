# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Wallpaper Engine "web" type wallpaper — a 4K Miku snow-scene wallpaper. The background image (`images/bg.png`) is rendered as a CSS `background` layer, and a transparent WebGPU canvas overlays animated particle snow on top via browser compositing.

## Development commands

```bash
pnpm lint          # Run both oxlint + eslint (with auto-fix)
pnpm lint:oxlint   # oxlint only (fast Rust linter)
pnpm lint:eslint   # eslint only (JS rules + Prettier skip)
pnpm format        # oxfmt formatter (targets js/)
```

**No build step** — this is vanilla JS (ES modules) served directly to the browser. Wallpaper Engine loads `index.html` as specified in `project.json`.

**No test suite** — testing is done by loading the wallpaper in Wallpaper Engine: create a "Web"-type wallpaper, set its URL to the local `index.html` path (`file:///...`), then refresh the wallpaper after JS edits (see README §开发流程).

pnpm pinned via `packageManager` (`pnpm@11.22.0`).

## Architecture

Three JS modules loaded from `index.html` via a single `<script type="module" src="js/settings.js">` entry point:

| Module             | Responsibility                                                                                                                                                                                                                                                                                                                                  |
|--------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `js/settings.js`   | Wallpaper Engine property listener bridge. Implements `window.wallpaperPropertyListener.applyUserProperties` — the sole interface between the engine and the wallpaper. Pure forwarding; no business logic.                                                                                                                                     |
| `js/background.js` | CSS `background-size` switching for the `#background` div. Exports `setDisplayMode(mode)` where mode is `cover`/`contain`/`auto`.                                                                                                                                                                                                               |
| `js/particles.js`  | WebGPU particle system. Compute shader steps particle physics (base motion + wind/turbulence displacement + boundary wrapping), vertex shader does instanced billboard quads with temporal extrapolation of both the base velocity and the wind-phase fractional step, fragment shader renders radial-gradient circles. Exports `start()`, `setCount(n)`, `setSpeed(s)`, `setPink(bool)`. |

**Data flow:** Wallpaper Engine → `wallpaperPropertyListener.applyUserProperties(props)` → per-property branches call into `particles.js` or `background.js` → GPU buffers / CSS updated.

## Wallpaper Engine integration

The `project.json` defines the wallpaper metadata and user-adjustable properties. The `type: "Web"` field signals this is a web wallpaper — Wallpaper Engine embeds it as a browser view and calls `applyUserProperties` on the global listener. The wallpaper is published to the Steam Workshop (id 3755473060).

**Properties** (defined in `project.json` → `general.properties`):

| Key           | Type   | Range/Options          | Default | Effect in `js/settings.js`                                          |
|---------------|--------|------------------------|---------|---------------------------------------------------------------------|
| `aNumber`     | slider | 0–1000                 | 500     | → `particles.setCount(n)`                                           |
| `aSpeed`      | slider | 500–3500               | 2000    | → `particles.setSpeed(s)` (larger = slower; `speedFactor = 1500/s`) |
| `customcombo` | combo  | cover / contain / auto | cover   | → `background.setDisplayMode(m)`                                    |
| `custompink`  | bool   | —                      | false   | → `particles.setPink(b)`                                            |

`general.properties.schemecolor` is an engine-UI scheme color (order 0) — not handled in JS.

## WebGPU particle system design

**Buffer strategy:** Two storage buffers (`_buf0`, `_buf1`) allocated once at `MAX_COUNT = 1000`. Active particle count is a uniform — `setCount()` only updates the uniform and workgroup dispatch count; buffers are never resized on count changes, avoiding GPU allocation jitter and particle-state resets; `setCount(0)` stops the rAF loop, clears the canvas of frozen particles (one no-draw render pass), and positive values restart it.

**Compute pass:** Ping-pong dispatch — `_currentSrc` toggles each step. Each thread processes one particle: `position += velocity × speedFactor`, plus four wind/turbulence displacement differences (see the wind model below), then a per-axis modulo wrap; the particle's clock field `_p0` advances by `PHASE_PER_STEP`. `_workgroupCount = ceil(count / 64)`; threads with `i >= count` return early and keep their last written state.

**Wind/turbulence model:** Turbulence sway, lateral wind, and depth wind are part of the simulation, not a render-time offset. The compute shader advances each particle's own clock (`_p0`) by `PHASE_PER_STEP = 1/60` per physics step — one phase unit is one real second, deliberately independent of `speedFactor`, so the ~35s gust pulse and every sway frequency keep the same timing at any speed setting — and adds the *difference* of the field between the old and the new phase (`swayX`/`swayY`/`windXOffset`/`windZOffset`, declared once in the `WGSL_COMMON` chunk that both shaders interpolate, so the two sides cannot drift apart) to the position: the field then acts as a velocity-like drift, so its contribution stays bounded instead of accumulating as an absolute offset. `TIME_WRAP = 200π` is a common period of every frequency in play (each `100 × f` is an integer), so wrapping the phase is seamless. Near-camera particles damp all four displacement terms by the same `nearScale = clamp((cameraZ - p.posZ) / 500, 0.35, 1)` on both sides (the compute uniform therefore carries `cameraZ` too). The vertex shader repeats the same difference formula with the fractional-step phase `extrapPhase`, so physics and rendering stay on one trajectory — there is no render-only displacement left for the visibility gates to compensate for.

**Render pass:** Instanced draw (4 vertices × `_count` instances, `triangle-strip`). Vertex shader does perspective projection + temporal extrapolation: it advances the stored position by the remaining fractional step for both the base velocity (`extrapFactor = speedFactor × (accumulator / FIXED_STEP)`) and the wind phase (`extrapPhase = (accumulator / FIXED_STEP) / 60`) — turbulence and wind are already part of the simulated position (see the wind model above), so the rendered position is the simulated one. Screen radius is capped at `MAX_SR` (48 px) and particles fade out below `NEAR_DIST` (35 world units) to prevent near-camera fill-rate spikes; a symmetric far fade (from `cameraZ + 1000` to `cameraZ − zMin`, the box's far z-boundary — `zMin` is inset by `EDGE_MARGIN = 115` world units so the x wrap plane stays outside the frustum at the fade's end; driven by the pre-wrap predicted depth `cameraZ - pz` rather than the stored physics depth; the start is `min(cameraZ + 1000, farFadeEnd − MIN_FAR_FADE)` with `MIN_FAR_FADE = 32`, so `edge0 < edge1` survives any later retuning of the JS constants, while today it always resolves to `cameraZ + 1000`) makes all boundary wraps happen at fully transparent depths — no far particles popping in/out of thin air, no far-edge flash; particles are hard-gated to invisible when either the stored physics depth (`cameraZ - p.posZ <= 0`, which also covers a wrap landing behind the camera) or the pre-wrap predicted depth (`cameraZ - pz <= 0`) is at or behind the lens — the second gate is what stops a prediction that crosses `zMax` from being wrapped onto the far plane, where the near fade no longer applies, and showing up there at full opacity; particles whose predicted position is outside the frustum's lateral extent fade by their overshoot (fade band = the billboard's on-screen radius plus 8 world units, min 12 — no wind margin is needed now that the wind is part of the position being tested); fully faded / behind-camera particles collapse to zero-area quads (no fragment cost). Fragment shader outputs premultiplied alpha (blend srcFactor `one`) and draws radial-gradient circles (`premultiplied` alpha mode on the canvas context). Uniforms are small and rewritten only when their content changes: the render uniform is 12 f32 (48 B) and `handleFrame` rewrites just `[extrapFactor, extrapPhase]` at offset 24 (two f32) per frame; the compute uniform is 7 fields (28 B, including `cameraZ` for `nearScale`). Per-frame JS is allocation-free except WebGPU-mandated objects: `_renderPassDescriptor` is a preallocated template and `_colorAttachment` (a cached alias of its `colorAttachments[0]`) is the only per-frame mutation — a zero-cost micro-optimization whose benefit is far below one frame's GPU work; keep the alias rather than inlining the lookup chain.

**3D world:** Box world with dynamic per-axis bounds computed by `_updateWorldSize()` on load and after each resize. x half-width (`_worldHalf`) comes from the far-plane frustum extent at `MAX_DIST` (= `CAMERA_Z + 1000`): `halfH = tan(FOV/2) × MAX_DIST`, `halfW = halfH × aspect`, `_worldHalf = max(ceil(max(halfW, halfH) × 1.1), 2000)`. y half-height (`_yHalf`) is the frustum half-height at the far-fade end × 1.1, and z spans `[CAMERA_Z − farFadeEnd, CAMERA_Z + 1]` — the visible depth band plus a 1-unit wrap destination behind the camera. `farFadeEnd` is provably greater than `MAX_DIST` for every aspect ratio (the `2000` floor plus the `1.1` margin reduce the formula to ≈`2200 − 150/aspect` in landscape and `min(2457/aspect, 3000)` in portrait, i.e. ≥ ~2073), which is what keeps the shader's far fade well-formed. The `MAX_COUNT`/default-count budget (1000 / 500) maps to ~300 / ~150 flakes on screen on 16:9. Keeping y/z tight (instead of a full cube) stops most of the budget from idling behind the camera or beyond the far plane: ~25% of particles are on-screen at any moment on 16:9 (vs ~7% for a cube; the geometric ceiling for uniform spawn in a box enclosing the frustum is 1/3). Boundary wrapping is a per-axis modulo normalization (`wrapRange`) applied identically in the compute physics and in the vertex-shader extrapolation, with the same bounds (`±worldHalf` for x, `±yHalf` for y, `[zMin, zMax)` for z), so any overshoot — beyond one world period, or a position left outside a world that shrank on resize — is normalized in a single step instead of being corrected once per frame; the y/z bounds and the `EDGE_MARGIN` inset keep every wrap plane outside the frustum at all visible depths, so wraps always land off-screen or fully faded. (No uniform carries the world's x total width — both shaders derive their x bounds from `±worldHalf`, and JS keeps only the half-width, so there is no derived value to keep in sync.) Initial positions spawn uniformly over the box.

**Resize:** Debounced (150ms) rebuild shared by `window.resize` and a `matchMedia('(resolution: Xdppx)')` change listener — the latter catches the cross-monitor / system-scale case where only `devicePixelRatio` changes and no `resize` event fires (otherwise the canvas would keep the old backing-store resolution and stay blurry). `_applyCanvasSize()` recomputes the backing store, `focalLength` and the world; `_watchDevicePixelRatio()` re-arms the media query for the new dpr. The same `_applyCanvasSize()` runs once at module load.

**Failure handling:** Device loss (`.lost`), GPU validation errors (`uncapturederror` — these never throw JS exceptions), and in-frame sync errors all funnel into `_shutdown()`, which nulls `_device`/`_queue` **and every GPU resource reference** (buffers, pipelines, uniform buffers, bind groups, context — each holds a device reference, so nulling only `_device` would keep the dead device graph alive) and truly stops the rAF loop (frameLoop only requests the next frame while `_rafId` is non-null); the CSS background layer keeps rendering. Device loss is retried: `_scheduleRetry()` re-runs `_initGPU()` after 2 s, bounded by `MAX_INIT_ATTEMPTS = 3` attempts *per episode*; `_initGPU` is a thin guarded wrapper (re-entrancy + attempt counter) around `_initGPUResources()`, whose success path clears that counter and sets `_everReady`, and `_abortInit()` re-schedules only when `_everReady` — i.e. only on a machine that has already proved it can run WebGPU. So a machine without WebGPU never spins, while a wallpaper left running for days gets a fresh retry budget after every loss instead of exhausting one process-wide count. `uncapturederror` is deterministic and is deliberately **not** retried. `_initGPU` calls `start()` at the end of its success path to cover the race where the engine calls `start()` before the device is ready (start() is gated on `_device`). A missing `#canvas` is deliberately *not* a fatal module error: the top-level guard logs once and `_applyCanvasSize()`/`_initGPUResources()` early-return, so the module still evaluates and `settings.js`'s property bridge (including `background.js`'s display mode) keeps working with the particle layer simply absent. `_shutdown()` intentionally leaves the canvas as-is instead of blanking the frozen frame — device loss makes GPU submissions no-ops, and a non-GPU blank would turn the ~2 s loss→retry gap into "snow disappears, then returns", while a still snow field degrades more gracefully and is cleared by the next resize anyway.

**Device init:** `_initGPU` calls `requestAdapter()` without `powerPreference` — Chromium on Windows ignores that option (crbug.com/369219127) and logs a warning; on dual-GPU machines the GPU is chosen by the OS (Windows Settings → System → Display → Graphics for wallpaper32.exe / webwallpaper32.exe).

## Linting & formatting configuration

- **oxlint** (`.oxlintrc.json`): `correctness` category at error level, plugins: `eslint`, `unicorn`, `oxc`. Browser env. Four style rules — off by default — are enabled explicitly: `curly` (braces on every `if`/`for`/`while` body), `object-shorthand`, `prefer-arrow-callback`, `prefer-template`.
- **eslint** (`eslint.config.js`): Extends `@eslint/js` recommended, `eslint-config-prettier` (formatting rules skipped), oxlint plugin for compatibility. Browser globals. One block, `app/eslint-only-style`, sits **after** `skipFormatting` and adds the two rules oxlint cannot provide: `semi` (re-enabled, because eslint-config-prettier turns it off) and `camelcase` (oxlint has no such rule; it deliberately ignores all-caps constants such as `MAX_COUNT`).
- **oxfmt** (`.oxfmtrc.json`): 2-space indent, single quotes, trailing commas, semicolons, 80-char print width. Formatting rules live here rather than in the linters — oxlint implements none of them, so a formatting rule added to `.oxlintrc.json` fails with "Rule not found".

## Editor setup

`jsconfig.json` enables type checking (`checkJs: true`, `strict: false`) with `@webgpu/types` for WebGPU API completions. The `moduleResolution: "bundler"` setting allows ES module imports to resolve correctly in the IDE.
